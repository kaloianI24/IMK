## 3. A-2 — is the new rule correct? Does it regress anything?

**It is correct, and I found no legitimate request that regressed.** Here is the reasoning, executed:

**The rule discriminates *absent* from *present-but-empty*, and only the latter changed.**
`url.searchParams.get()` returns `null` **only** when the parameter is absent. So B-1's change moves exactly one input class: `?__imk_route=` (present, empty).

- **A platform that DROPS the query entirely** → the parameter is absent → `null` → the header contingency still works (A4: header → 401) and a bare entry point still gives the loud 500 (A6). **Unaffected.**
- **A platform that sends an EMPTY parameter** → refused with 404. That is the intended rule.

**The one input whose outcome changed** is `?__imk_route=` (empty) **plus** an `x-imk-route` header naming a route. Before wave 15 that combination fell through to the header and the handler ran (401); now it is a clean 404. That is precisely the behaviour the brief ordered ("never a fall-through to the header"), and it is not a legitimate configuration: a platform that drops the query sends *nothing*, not an empty parameter. **No legitimate request regressed.**

**Everything else is byte-for-byte unchanged** — proved, not argued:
- A legitimate deployed request keeps its client query and loses the carrier (A12).
- The local/dev shape (path resolves directly) is untouched, including a direct-path request that happens to carry an empty carrier (A11).
- A duplicate carrier parameter: `searchParams.get` returns the **first** value, so `?__imk_route=/api/portal/session&__imk_route=` resolves normally (the trailing empty value is harmless), while a *leading* empty value refuses the route. (probe2 R4)
- **No product code sends an empty carrier.** A repo-wide scan found `__imk_route` only in the router, the two entry points and the deploy gate — never in the front-end or in any request builder. (probe3)

**Residual risk I cannot rule out (not a regression):** if the platform's merge lets the **client's** query win on a key collision, a client that appends `?__imk_route=` (or any `__imk_route` value) to a portal URL overrides the rewrite's carrier. That was already true in wave 13 (my MAJOR-1) and wave 15 does not change it. The empty-carrier case is now a clean 404 instead of the old 500; the *self-inflicted* break is the same either way.

**One behaviour change worth stating plainly (a MINOR, see F-2):** the empty-carrier refusal is now **silent** — no log line at all — where the pre-wave-15 behaviour produced a *logged* loud 500.
