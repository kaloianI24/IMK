## 2. D-4 — the CF moderation twin answered 404 where Vercel answers 501 (CLOSED)

**Owner: Backend (QA raised it twice and named it mine).**

### The defect

`site/functions/api/moderate/review.ts:77` returned an empty array for a
missing store:

```ts
if (!fs.existsSync(REVIEWS_FILE)) return [];   // ← an empty store
```

The Vercel twin (`api/moderate/review.ts:85`) throws
`StoreUnreachableError` for the same situation and answers
`501 {code:'unimplemented'}`.

`501` is right and `404` is wrong here: `404 review not found` is the exact
"your quote is gone" outcome. QA's B6 pinned the expectation — *"the CF
twin must answer 501 for a missing store like the Vercel tree … a 404 reads
as 'your quote is gone'"*.

### The fix — one file, one function

`site/functions/api/moderate/review.ts` → `readReviews()`:

```ts
function readReviews(): Array<Record<string, any>> {
  const fs = edgeFs();
  if (!fs) throw new StoreUnreachableError();
  // A MISSING file is not an empty log (parity with api/moderate/review.ts):
  // it is a store this target cannot serve. ...
  if (!fs.existsSync(REVIEWS_FILE)) throw new StoreUnreachableError();
  const content = fs.readFileSync(REVIEWS_FILE, 'utf8');
  return parseJsonlStrict(content, REVIEWS_FILE);
}
```

The `throw` is already handled 40 lines below by the existing
`catch (err)` block, which maps `StoreUnreachableError` → `501
{code:'unimplemented'}` and `isStorageCorrupt(err)` → `500
{code:'storage'}`. **No other file changed. No handler signature changed.
The moderation contract (`ref`, `decision`, `revision`, `sig`, `ts`) is
untouched.**

## 6. Two findings from this pass — reported, not fixed

### 6.1 Four shared-utility files under `api/` have no default export — **LOW severity, but real**

`api/lib/jsonl.ts`, `api/lib/notifications.ts`, `api/lib/rate-limit.ts` and
`api/portal/session.ts` are shared modules, not routes, yet they sit
*inside* `api/`.

Vercel's rule, quoted from its own docs
(`/docs/functions/runtimes/node-js`): *"Vercel creates a separate function
for each supported source file in the root `api/` directory … Keep shared
utilities and route modules outside `api/` and import them from your
function entry point."* And from `/docs/functions/configuring-functions/advanced-configuration`:
*"Vercel ignores files that start with an underscore, `_`, or with `.`, and
files ending `.d.ts`."*

**Severity, stated precisely:**

- Vercel will try to build a function for each of the four files. Each has
  no default export, so at runtime the serverless launcher
  (`packages/node/src/serverless-functions/serverless-handler.mts`) finds
  no `default`, no HTTP-method export and no `fetch`, and throws
  *"Can't detect way to handle request"*. **That is a 500 on a dead URL, not
  a build failure** — it does **not** break the deployment and does **not**
  affect any real route.
- It costs 4 wasted functions out of 20 files under `api/`. On the **Hobby**
  plan, a no-framework project is *"limited to 12 Vercel Functions per
  deployment"* (`/docs/functions/runtimes#functions-created-per-deployment`).
  The repo has **16 route files + 4 helpers = 20**. If the project stays on
  Hobby, the deploy **will** hit that limit; on Pro/Enterprise there is no
  limit. **This is the one place where the stray files and the plan
  interact, and it needs an owner decision on the plan — not a code change
  from me.**

**Fix, when the plan is known (deliberately not done now):** move the four
modules to `site/shared/server/` (where `portal-session.ts` and
`magic-link.ts` already live and which is outside `api/`), then re-point
the 13 import sites. That touches import paths in ~11 handler files and
would need a re-run of every suite — a shared-tree change I will not make
unilaterally, especially with Frontend/QA/DevOps actively editing nearby
files.

### 6.2 The portal still cannot persist on Vercel — **unchanged, still T4**

A Vercel function has a **read-only filesystem** (only `/tmp` is writable),
so the file store under `site/data/` cannot be written by a deployed
function. The marketing site deploys and works; **the portal needs the
libSQL adapter (T4)**, which is blocked on the owner's Turso-vs-Neon
decision and therefore not built. Nothing in this wave changes that, and
nothing in this wave pretends otherwise.
