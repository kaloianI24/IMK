### HIGH

#### H1 — Review form bypasses the project's own abuse pipeline and sends data to a third party
**Location:** `site\src\components\ReviewForm.astro` (lines 1–7, 14–18, 189–239)
**Why it matters:**
- The form posts to a Formspree placeholder `https://formspree.io/f/YOUR_FORM_ID` — a live third-party processor holding customer-submitted names, emails, and reviews, with no business agreement visible.
- It bypasses `functions/api/contact.ts`, which is the project's single, spec-mandated submission endpoint (`spec §6 I-7: "All form submission and webhook work goes through /api/contact. No client-side email send, no third-party form host."`). The contact function has Turnstile verification, rate limiting (KV/in-memory), honeypot, time trap, body caps, Resend email, redacted logging, and an optional signed webhook. None of it applies to the review form.
- The honeypot is client-side only (`display:none` input named `website`); trivial for bots to bypass. No server-side honeypot check, no Turnstile, no rate limit on reviews.
- No consent handling / no link to privacy policy for the review data.
- CSP `form-action 'self'` in `public\_headers:7` would block a POST to Formspree anyway, so even the intended submission path conflicts with the deployed header policy.
**Fix:** Route the review form through `/api/contact` (extend the contact contract to accept a `review` payload, or reuse the contact shape with a `type=review` discriminator), add Turnstile + server-side honeypot + rate limit, remove the Formspree placeholder entirely, and add a privacy/consent note. Until then, reviews cannot be safely collected.
**Verified:** Yes (read both files and spec).

#### H2 — Placeholder site URL would ship canonical URLs pointing at nothing
**Location:** `site\astro.config.mjs:6` — `site: (process.env.SITE_URL || 'https://www.ixi.example').replace(/\/$/, '')`
**Why it matters:** `SITE_URL` is unset locally, so `site` resolves to `https://www.ixi.example`. This leaks into the sitemap (`@astrojs/sitemap`), canonical `<link>`, OG tags, and JSON-LD `url`. If built and deployed as-is, every canonical URL and the sitemap point at a non-existent domain, breaking SEO and making the site unreachable via its own sitemap.
**Fix:** Require `SITE_URL` at build time (fail the build if unset), or commit a `.env.example` with the real domain and document that production must set `SITE_URL`. Do not ship the `.example` placeholder.
**Verified:** Yes (read config + confirmed no `.env` file exists).

#### H3 — HSTS enabled before the domain is stable
**Location:** `site\public\_headers:6` — `Strict-Transport-Security: max-age=31536000; includeSubDomains`
**Why it matters:** `spec §8` explicitly states HSTS is "added only post-launch" and "DO NOT enable before domain stabilises." Enforcing a one-year HSTS policy on a domain that may change (or on `*.pages.dev` preview) can lock visitors out via hard-failed HTTPS if the domain or hosting moves.
**Fix:** Comment out HSTS until the production domain is stable and launched, per the spec. Re-enable with preload only at launch.
**Verified:** Yes (read `_headers`).

### MEDIUM

#### M1 — Duplicate brand/token sources of truth (guaranteed drift)
**Location:** `design\tokens.css` vs `site\src\styles\tokens.css` (verified byte-identical, both 177 lines); `design\wordmark-light.svg`, `design\wordmark-dark.svg`, `design\favicon.svg` vs `site\src\brand\logo.ts` + `site\public\favicon.*`
**Why it matters:** Both `tokens.css` files claim to be "single source of truth" in their headers. They are currently identical but nothing enforces it. Any edit to one without the other causes visual drift. The logo artwork likewise exists in `design/` (SVG exports) and is regenerated into `site\src\brand\logo.ts` by `scripts\gen-brand.mjs` — two touchpoints for the same asset.
**Fix:** Declare one authoritative source: `site\src\styles\tokens.css` (consumed by the build) is the runtime source of truth. Delete `design\tokens.css` or replace it with a one-line pointer/import. For the logo, keep `src/brand/logo.ts` (generated) as source of truth; treat `design/*.svg` as the owner's raw artwork input to `gen-brand.mjs`, not as deployable assets. Add a CI check that the two token files match (or remove the duplicate).
**Verified:** Yes (files identical).

#### M2 — Naming inconsistencies across files, collections, and frontmatter
**Location:** Multiple (see below)
**Why it matters:** A new contributor cannot guess the canonical name for anything.
- Collection key is `cases` in `site\src\content.config.ts:32`, but `spec §2` calls it `caseStudies`; the directory is `src\content\cases\` while spec §2 lists `src\content\case-studies/`.
- Service frontmatter field is `cta` (`content.config.ts:28`, `audit.md:33`), but `spec §2` and `spec §5` define `primaryCTA`.
- `site\src\pages\index.astro:17-22` `serviceIcons` keys carry the `.md` suffix (`'workflow-automation.md'`) while `s.id` already includes it — works but is redundant and confusing.
- CSS class naming is only partially BEM: `hero-section__logo-wrapper`, `social-proof__text`, `review-form__card` are BEM-ish, but `container`, `section`, `grid-2`, `grid-3`, `card`, `btn`, `btn-primary`, `eyebrow`, `muted` are flat utility-like names with no block prefix.
- `hero-section__logo-wrapper` (`index.astro:51`) now contains only the symbol mark — the name implies a logo wordmark lockup that no longer exists there.
- Script names in `site\scripts\` mix `_debug-*`, `_contrast*`, `_audit`, `_qa-sweep`, `_verify-*`, `gen-*`, `trace.mjs` with no convention.
**Fix:** Adopt one house standard (recommend BEM for blocks/elements, kebab-case files, collection/frontmatter names aligned to the spec: `caseStudies` collection in `src/content/case-studies/`, frontmatter `primaryCTA`). Rename `hero-section__logo-wrapper` to `hero-section__mark` (or keep the wrapper but align the name to its single-child content). Align script names (`tools/` prefix for one-off diagnostics, `scripts/` only for committed generators).
**Verified:** Yes (read all cited files).

Move `_qa-sweep` into `qa/` with a relative path parameter. Re-run `astro check` to confirm 0 hints.

Inline styles bypass the token system and are harder to maintain; the scoped CSS already declares the same values (`index.astro:150-159`).

**Verified:** Yes (read file; confirmed earlier stale-CSS incident).

#### L2 — CSP in `_headers` does not match the spec'd analytics/defaults
**Location:** `site\public\_headers:7`
**Why it matters:** `spec §8` defaults analytics to Plausible (`connect-src https://plausible.io`) and includes `www.googletagmanager.com` only if opted into GTM. The shipped `_headers` has no Plausible host in `connect-src`, lists `api.resend.com` (a server-only call, unnecessary client-side), and includes `script-src` entries that may or may not match the live page. Spec §8 also says script hosts must be verified against a live page load in M5 — not yet done.
**Fix:** Align `_headers` CSP to `spec §8`: Plausible connect-src by default, no GTM unless opted in, remove unnecessary `api.resend.com` from client `connect-src`, and verify exact hosts against a live page before M6.
**Verified:** Partially (read `_headers` and spec; live verification not performed).

#### L3 — No `.env.example` committed, no env separation in repo
**Location:** Repo root — `.env` absent (verified False); `spec §12` requires `.env.example` committed, `.env*` gitignored.
**Why it matters:** Developers deploying the site have no documented list of required build-time vs server-time variables (`TURNSTILE_SITE_KEY`, `RESEND_API_KEY`, `SITE_URL`, etc.). Risk of secrets accidentally committed or builds failing for missing vars.
**Fix:** Commit `.env.example` listing every variable with public vs server-only marking; add `.env*` to `.gitignore`.
**Verified:** Yes (`.env` absent).

#### L4 — Review form markup/a11y polish (non-blocking)
**Location:** `site\src\components\ReviewForm.astro`
- The `<script>` (line 189) uses TypeScript `as` casts in a non-`lang="ts"` script block. `astro check` currently passes (0 errors), so it is not a build failure, but it is non-idiomatic and fragile.
- Star rating (`lines 50-61`): five visually-hidden radio inputs with `★` labels. Focus indication on the hidden inputs is not visible, so keyboard users cannot tell which star is focused — a WCAG keyboard-visibility concern.
- The review `textarea` has no `autocomplete` attribute (minor).
**Fix:** Add `lang="ts"` to the script (or drop the casts), add visible focus styles to star labels (`focus-visible` outline), and consider `autocomplete="off"` on the textarea.
**Verified:** Partially (read file; `astro check` passes so casts are not errors; keyboard focus not tested).

## Architectural recommendation (from this audit)

The review/testimonial feature should **not** use Formspree. The repo already contains a purpose-built, spec-compliant submission pipeline at `functions/api/contact.ts` (Turnstile + honeypot + time trap + rate limit + Resend + redacted logging + optional signed webhook). Extend that pipeline to accept reviews (e.g. a `type` discriminator), wire `ReviewForm.astro` to `POST /api/contact` with the site's Turnstile site key, and store approved testimonials in the content layer (`src/content/testimonials/` or frontmatter) so they ship as part of the static build — matching the moderation model already described ("submissions go to an inbox; approved ones get written into the site and rebuilt").
